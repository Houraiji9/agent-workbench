# 项目工作群

工作群把同一项目的讨论、派活和成员回报放在一起。负责人是群里的角色，可以选择 Codex 或 Claude；工作台通过本机客户端真正启动成员，保存调用状态和原生会话。群内工作与原有 Task、Run、独立审查及用户验收分别记录，可按需要关联。

从 0.4.26 起，API 型 Agent 也能加入工作群或担任负责人。它不需要安装供应商 CLI，由工作台后端请求模型并执行工具循环。

## 添加 API 型 Agent

在“团队”中选择“添加 API 型 Agent”，填写名称、服务地址、API Key 和精确模型名。默认协议是 OpenAI 兼容 Chat Completions；使用 Responses 的服务在协议选项中切换。服务必须支持对应协议的函数工具调用，单纯能返回聊天文本不代表能执行任务。地址可填写供应商给出的完整端点，或包含版本前缀的基址，例如 `https://api.openai.com/v1`；工作台保留自定义路径，不猜测模型或替换供应商。

保存后，这位成员出现在工作群的成员和负责人列表。API Key 只提交到本机后台并使用 Windows 当前用户 DPAPI 加密；编辑时留空保留原 Key，清除须使用明确的清除操作。“检查本机配置”不联网、不调用模型，也不证明账号或模型在供应商端可用。首次派活才会实际请求模型，消耗已配置服务的正常额度。

API 成员可以列出目录、读取 UTF-8 文本、创建文件或按读取到的 SHA-256 修改文件，还能使用工作群派活、讨论、收件箱与已授权外部服务工具。文件工具限定本群目录并保护凭据、私有数据和目录链接；它没有任意 shell 工具，需要运行命令时可派给群内已有 CLI 成员。Windows 同一用户进程不等于操作系统沙箱。

把 API 成员设为负责人后，仍通过“交给负责人”发送目标。它能明确派给其他 API 或 CLI 成员，成员结束后由调度器自动续接负责人。会话与群、成员、模型及配置版本绑定，私有协议转录加密保存，群中只显示公开结果。已有调用进行中时不能修改配置；闲置时修改会开启新配置的会话，保留旧会话历史。

工具循环有轮数、工具次数、响应体及会话大小限制，不自动重试可能付费的模型请求。认证、额度、协议不支持、超时或工具错误会保留真实状态。工具已开始但结果未持久化时，不自动重放可能有副作用的操作；停止当前循环不代表已提交给外部服务的异步任务也已取消。

协议实现参考 [OpenAI 函数工具调用文档](https://developers.openai.com/api/docs/guides/function-calling) 与 [Responses 迁移说明](https://developers.openai.com/api/docs/guides/migrate-to-responses)。不兼容这些协议的供应商需要另外适配。

## 使用

从导航的“工作群”或项目里的工作群入口进入，选择项目并创建群。选择负责人、成员和项目工作目录后，“创建并启用工作群”保存这一范围的自动协作授权。之后不需要为每条普通派活重新批准或复制执行单。

输入框提供三种发送方式：

- **交给负责人**：说明目标，负责人接收新一轮消息，可以用工作群工具把子任务派给其他成员。
- **派给指定成员**：直接把任务加入该成员的执行队列。成员忙时排队，不占用用户转述。
- **只发到群里**：保存讨论或补充资料，不自动启动模型。Agent 需要其他成员处理时，使用明确的派活操作。

成员回报显示在群里。调度器把结果送回发起派活的成员；原生会话在同一群成员下恢复。不同群的会话不会共用。每次请求的自动接话次数可在群设置调整，用于避免无休止的互相回复。

“执行中”表示客户端正在运行；“已回报”表示拿到了该成员的结果，不能代替文件核验、独立审查或用户验收。错误会保留真实失败状态。停止工作会暂停群内派发并请求结束相关进程；进程是否确实退出单独核对。服务重启时不盲目重跑未知的旧调用，确定可继续后再恢复该成员会话。

## Agent 调用

配置了工作台 MCP 的管理或执行会话可通过这些入口协作：

| 工具 | 用途 |
| --- | --- |
| `list_workgroups` | 查当前身份可参与的项目群 |
| `get_workgroup_context` | 按消息序号读取群成员、消息和实际调用状态 |
| `post_workgroup_message` | 以本人身份发言，普通消息不会触发自动接话 |
| `dispatch_workgroup_task` | 明确派活或请求成员讨论，返回可查询的调用编号 |
| `get_workgroup_job` | 查询派活状态与回报 |
| `get_workgroup_inbox` / `ack_workgroup_inbox` | 读取、确认本成员收到的消息 |

工作台启动的成员会自动获得该次调用的群工具连接。调用凭据绑定实际群、成员与作业，不能通过修改参数冒充别人。普通外部 Agent 会话仍使用现有工作台 MCP；工作台不会接管用户在其他客户端里已打开的聊天。

群成员还可发现并调用“团队 / 外部服务”里已配置的 API、CLI 和 MCP 能力。连接必须允许该项目和真实 Agent；原有消费开关、调用额度和产物处理仍生效。成员不接收原始密钥，后续会话可查询同群本人之前创建的异步调用。

管理调用可在添加成员时指定 `model`，页面会把它标为“调用配置”，实际模型仍以本次客户端回传为准。Harness 会优先使用已有 headless 路由；只有显式选中的模型未在 headless 注册、且在 desktop 配置中唯一存在时，才把对应供应商配置临时带入本次调用。它保留原有凭据引用，不迁移桌面插件或改动全局默认设置；歧义、同供应商策略冲突和不能安全保存的内联认证配置会明确报错。没有指定模型时，继续使用原生 headless 默认配置，不因缺少密钥而自动切换账号或模型。

## 执行范围与证据

工作台限制群工具、目录选择、成员身份和调度范围；本机 CLI 沿用自身的权限机制。工作群授权不会覆盖客户端的明确拒绝，不启用跳过全部权限检查的参数，不修改全局 Agent 配置。Windows 同一用户下的 CLI 进程不等于操作系统层面的完整隔离，不能把提示中的目录要求宣传成独立沙箱。

群中显示可公开的最终答复和状态，不把客户端内部推理、原始环境变量或凭据当作群消息。原生会话 ID、错误和未知型号如实记录，不从展示名称猜测实际模型。

工作群功能参考了 [Codync 的群与团队设计](https://www.codync.dev/docs/teamwork) 和 [Parley 的收件箱、会话及回执设计](https://github.com/auspex0/parley/blob/main/DESIGN.md)。当前实现在原工作台内维护消息与调度，不依赖安装另一套完整工作台。
